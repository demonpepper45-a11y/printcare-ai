# 结构化故障单与分支追问（2026-11-17）

负责人：当前 Codex Agent。分支 `feat/fault-ticket`，基于 `84936c6`。
范围：把用户描述整理为结构化故障单；信息不足时只追问会影响下一步分支的字段；不修改 50 题预期。

## 结果

| 场景 | 行为 |
|---|---|
| “打印时不出料，已经重新装料，未解决” | 返回 `needs_clarification`，不调用模型；故障单记录机型、现象、阶段、已尝试；追问错误码与供料方式 |
| 用户回答“使用外置料架，没有错误码” | 合并进同一故障单；`error_code=无`、`feed_method=外置料架`；检索时带上原现象；返回 answered，给出官方热端堵塞方向与引用，不再继续追问 |
| “挤出机堵料怎么清理？”（已有具体排查请求） | 不触发确定性追问，继续走原回答/安全流程 |
| API / 页面 | `fault_ticket` 随聊天响应返回；页面显示“故障单”，未知字段标“待确认” |

## 故障单字段

- 机型、现象、错误码、耗材、供料方式（外置料架 / AMS lite / AMS）、发生阶段、已经尝试。
- 未知保持为空；用户明确说“没有错误码”记为 `无`，不再重复追问。
- 多轮合并：新信息补充旧字段，不覆盖已知值；机型切换清空旧故障单。
- 已追问字段记录在 `asked`，避免同一字段反复问。

## 追问规则

仅在 `no_extrusion`（不出料/没出料/挤不出）且用户尚未提出“清理/拆/检查/步骤/堵塞”等具体请求时，在调用模型前追问：

1. 屏幕是否显示错误码或提示？
2. 耗材是外置料架还是 AMS lite 供料？

两项都已知或已追问过后，进入正常检索与回答。其他类别（堵料、热床、首层、HMS 等）仍由模型按资料判断是否 `needs_clarification`，避免对所有问题强行套问卷。

## 实现

- 新增 `printcare.assistant.fault_ticket`：提取、合并、分支问题、序列化。
- `Session` 保存故障单；`ChatResult` 与 API `ChatResponse` 返回 `fault_ticket`。
- 短回答（如“外置料架，没有错误码”）会与已记录现象合并后检索，修复“补充信息后查不到原问题”的缺陷。
- 页面新增故障单展示；`missing_information` 增加 `error_code`、`feed_method`、`stage`。
- 故障单提示只注入“不出料”流程；否则会改变其他问题的回答形态。
- 关键字段已收集后，提示明确要求直接给下一步排查方向/官方指南入口，不再追问耗材或阶段。
- 页面请求改为 `trust_env=False` 直连本机 API，避免系统代理把 `127.0.0.1` 转发成 502。

## 验证

- `ruff check`、`ruff format --check`：通过。
- `unittest`：**247 项通过**（新增故障单 11 项、助手 3 项、API 2 项）。
- 真实模型（DeepSeek `deepseek-flash`）：
  - 首轮“不出料”：`needs_clarification`，0 次模型调用；
  - 补充“外置料架，没有错误码”：故障单合并，返回 `answered`，引用官方热端堵塞方向，不再追问；
  - 详细“挤出机堵料怎么清理”：不触发追问，返回指南入口。
- 全量 50 题：**50 通过 / 0 失败 / 0 跳过**，20 题指南模式，约 92,053 输入 / 17,836 输出 tokens，估算 $0.0490。
  - 第一次加入故障单提示时曾出现 4 题过度追问（A1-DQ-03、A1-SYN-01、A1M-SYN-01、A1-MT-01）；限制提示注入范围后 4/4 恢复，随后全量 50/50。
- 未改 50 题题目/预期；未重做专业人工验收。

## 限制

- 提取是规则式，覆盖常见中文表达；复杂否定、英文描述和未列出的口语可能漏提。
- 确定性追问目前只覆盖“不出料”分支；其他类别依赖模型判断，尚未逐类建立分支问题表。
- 故障单是会话内状态，不持久化；会话重启后丢失（第7/11项）。
- 自动评估与 AI 复核不等于专业人员签字；直接维修步骤仍默认关闭。
